# Environment, limits and trust boundary — DRAFT

The safety model is non-Byzantine: processes execute the delivered code, peers do not forge messages or identities, serialization preserves values, and network faults may delay, reorder, duplicate or lose genuine messages and partition nodes. A reply can arrive after its initiating term or RPC is obsolete. A node can crash between host operations, losing volatile state and outstanding tasks, and restart from its retained storage. Safety must not depend on eventual delivery, a timeout bound or a majority being available. Prove the implementation's protocol invariants rather than assuming them as environmental facts.

Genuine messages are actual code emissions, including erroneous ones. The fixed proof support records prior sends without assuming their Raft correctness. A host storage completion must correspond to the actual submitted operation and result; persistence-before-reply ordering is a program obligation, not a filter that removes actual early sends.

Raft group membership is fixed and finite for each group. The group identity and member set are trusted deployment inputs, consistent across nodes and restart; a retired identity is not reused for a different group's history. Shard assignment changes are application commands, not changes to the members of a consensus group. Invalid peer IDs, malformed external inputs and finite resource exhaustion need an explicit safe rejection/failure path at the real boundary, not an unchecked helper precondition.

Host networking, the MadSim scheduler/randomness, filesystem calls, mutex/task mechanics, channel delivery, Rust memory safety, `serde`/`bincode` value encoding and the Verus/vstd/Rust/SMT implementation are trusted components under their disclosed contracts. The host may transmit, store and expose outputs chosen by verified code. Voting, log selection, commitment, application authorization, snapshot decisions and recovery interpretation may not migrate into trusted host code. List exact host functions used by the final implementation and prove the verified side meets their preconditions. No unsafe or newly trusted consensus body may close a proof gap.

The selected MadSim filesystem is an in-memory simulator. At the pinned revision, `FsSim::power_fail` is a TODO and `File::sync_all` is a no-op; completed writes already survive node kill/restart. Creating a file truncates it, and operations on different files are not one atomic transaction. The supplied MadRaft `persist` skeleton writes `state` and `snapshot` separately. A crash between create/write or between those files must not be silently excluded. Tests on this simulator do not establish real-disk crash consistency, torn-write behavior or power-loss durability. The generator must disclose the model it proves and implement a coherent storage/snapshot protocol for it. Stronger disk guarantees require explicit host contracts and separate evidence; do not claim that a simulated `sync_all` has proved them.

The starting point has no reviewed full persistent-image encoding or serialization refinement. Whether to use a single consistent state/snapshot image, recoverable generations or another scheme is the generator's design choice within the existing API and size tests. Do not assume atomic multi-file replacement to validate a chosen representation. Corrupt media and Byzantine storage are outside this initial model; ordinary crashes and incomplete operations are inside it. Failure handling must not turn an unknown durable vote into permission to vote again in the same term.

Executable counters use finite Rust types; mathematical `nat` in the targets is only an abstraction. Prove checked increment/conversion and index bounds or stop safely at exhaustion without emitting unauthorized outputs. Do not assume that terms never overflow. Bounded memory may return an error or halt a node without violating safety; allocation success or unlimited resources cannot be silently used to claim liveness. A proof over an arbitrary fixed finite membership is distinct from testing a few small clusters.

Conditional liveness is OPEN and later. It needs separate eventual leader/timing/communication fairness, scheduling and resource assumptions plus progress proofs. Passing a finite deterministic test, having an election timer or proving the five safety targets establishes none of those temporal conclusions.
