# Progress — round 1

Implemented the previously absent 2A path in `madraft/src/raft/raft.rs`: randomized elections, periodic heartbeats, term handling, distinct-peer ballot collection, obsolete-reply checks, durable votes, and recovery. `madraft/src/raft/state.rs` is shared by Cargo and Verus; its executable methods check overflow, preserve an existing same-term vote, validate recovered vote records, and allow election only with a distinct-member majority in the matching term. `madraft/proof/progress.rs` verifies local election/recovery call compositions. No older candidate or solution was read.

Actual call chain: `RaftHandle::new` delegates to `try_new`, validates nonempty membership and `me < peers.len()`, calls `State::fresh`, restores records, then starts RPC handlers and the ticker. `start_ticker` calls `State::campaign`, persists, and calls `send_vote_request`; the latter constructs one RPC future per peer, binds its returned result to that peer, calls `Ballots::record`, `State::observe_term`, and `State::elected`. `Ballots::new` requires the constructor-established membership bound; `record` and `elected` require `Ballots::valid`, established by `new` and preserved by `record`. The async callers have not themselves been verified. Membership, distinct peer addresses, RPC provenance, locking and storage composition still need formal connection.

Inputs originate in `Endpoint::add_rpc_handler` or `Endpoint::call_timeout` completions. `RaftHandle::request_vote` serializes `Raft::request_vote`, calls the verified vote decision, awaits `persist`, then returns the reply. `heartbeat` calls `State::accept_leader` and persists before returning its term. `send_heartbeats` handles genuine delayed replies by monotonically observing terms. A shared async operation mutex serializes election mutations, journal submission/completion and reply release; proving this composition remains OPEN. There is no execution/history adapter yet: these actual mutations and emissions do not yet enter a proved global history, so all five fixed targets and output correspondence remain OPEN.

Persistence uses immutable `state`, `state.1`, ... records because the pinned simulator only obtains writable handles through truncating `File::create`; overwriting a previously acknowledged vote would be unsafe at a crash. `restore` reads the contiguous records, deserializes actual bytes, and calls `State::restore_successor` for each record to reject decreasing terms, incompatible same-term votes and invalid voter IDs. Incomplete created records return `InvalidData`; public `new` halts before installing handlers/ticker. Subsequent local method preconditions are unconditional or derive from fresh ballot construction, but the relation from durable records to all pre-crash votes/sends remains unproved. Journaling currently has no garbage collection, log entries, snapshots, group identity or application-state representation; this is a partial vote persistence path, not completed 2C/2D or a bounded storage solution.

Checks on the final source: `python3 scripts/check.py proof madraft/proof/progress.rs` PASS, 18 verified / 0 errors (log `runs/checks/1793334854093582114/proof.log`); foundation PASS; all three retained 2A tests (`initial_election_2a`, `reelection_2a`, `many_election_2a`) PASS separately for every seed 1–5; three added `election_checks` tests PASS on seed 1 (log `runs/checks/1793334898195178503/tests_seed_1_election_checks.log`). Added checks exercise a real vote across node kill/restart, incomplete record rejection, and maximum-term timeout without wrap. `python3 scripts/check.py safety` reports foundation/definitions/local proof PASS and all aggregate targets OPEN because `proof/implementation.rs` is absent. All other lab families remain untested and unfinished.

Failed approaches and repairs: the first ballot proof omitted the loop's unchanged-state invariant and a sequence-to-set lemma; the first call-composition proof exposed insufficiently precise vote/term contracts. These were strengthened and checked without assumptions. A panic-based incomplete-recovery test failed because MadSim treats task panic as a simulation failure; a fallible internal constructor now exposes the actual recovery error before any handler starts. One intermediate check reported candidate drift while contracts were edited; final 2A seed runs and the final added-test run completed without source edits.
